# 02 · 数据模型与事件词表

> biz-agent-platform 设计文档 · 地基篇。所有其他设计文档依赖本文。
> 依据：PLAN v1.1 §4.1/§8.1/§8.3；dsh-02（事件信封/seq/ignorable）、dsh-10（附件引用）、
> dsh-06（turn/step 边界）；agent_harness `persistence/models.py`（弃用对象）。

## 1. 设计原则

1. **append-only 会话事件日志是唯一事实源**：模型可见的内容、组件渲染状态、用户交互
   全部以事件追加；回显 = 回放（dsh-02 §1）。
2. **seq 连续性双侧校验**：写入前校验 `seq = max(seq)+1`；读取端校验连续（dsh-02 B2）。
3. **fail-closed 词表**：未知 type 且无 `ignorable` → 加载端拒绝重建并报错，不静默跳过
   （dsh-02 B3）。
4. **事件格式只加不改**：payload 带 `version`，字段永不重命名/改语义（PLAN 8.1）。

## 2. 表设计（PostgreSQL，Alembic 管理）

### 2.1 `platform_sessions`（会话头）

```sql
CREATE TABLE platform_sessions (
    session_id     UUID PRIMARY KEY DEFAULT gen_random_uuid(),
    user_id        VARCHAR(64)  NOT NULL,
    title          VARCHAR(255),
    domain         VARCHAR(64)  NOT NULL,             -- 业务域：financial / hr / ...
    plugin_set     JSONB        NOT NULL,             -- 创建时锁定的插件清单+版本 [{name,version}]
    plugin_set_hash VARCHAR(64) NOT NULL,             -- 用于快速比对（preset 锁，dsh-06 D2）
    status         VARCHAR(16)  NOT NULL DEFAULT 'active',   -- active / archived
    created_at     TIMESTAMPTZ  NOT NULL DEFAULT now(),
    updated_at     TIMESTAMPTZ  NOT NULL DEFAULT now()
);
CREATE INDEX idx_psessions_user ON platform_sessions(user_id, updated_at DESC);
```

规则：**会话创建后 `domain/plugin_set/plugin_set_hash` 不可变**（dsh-06 D2：历史是在第一套
工具下产生的）。
> 语义边界：锁定的是**工具集合形状**（插件 name 列表 + 各插件契约 hash），不是插件代码
> 版本。运行时是单版本加载（05 §1），插件升级后老会话 resume 用的是新代码。`plugin_set`
> 中的 version 仅作记录；加载时若与会话锁定版本不一致 → 记 warning 遥测，不阻断。
> 插件作者须遵守 §5 版本化规则，保证老会话事件可回放、工具行为向后兼容。

### 2.2 `platform_session_events`（事件日志，核心表）

```sql
CREATE TABLE platform_session_events (
    session_id  UUID        NOT NULL REFERENCES platform_sessions(session_id) ON DELETE CASCADE,
    seq         BIGINT      NOT NULL,                 -- 会话内 0 起单调递增，连续
    type        VARCHAR(64) NOT NULL,                 -- 事件类型（词表见 §3）
    time        TIMESTAMPTZ NOT NULL DEFAULT now(),
    data        JSONB       NOT NULL,                 -- 判别联合 payload（§3）
    ignorable   BOOLEAN     NOT NULL DEFAULT FALSE,   -- 未知 type 时 TRUE 才可跳过
    turn        INTEGER,                              -- 冗余：所属 turn（查询加速，可空）
    PRIMARY KEY (session_id, seq)
);
CREATE INDEX idx_pevents_type ON platform_session_events(session_id, type);
```

写入路径（唯一入口 `EventStore.append(session_id, type, data, *, ignorable, turn)`）：

```
BEGIN
  SELECT session_id FROM platform_sessions
  WHERE session_id = :sid FOR UPDATE                -- 锁会话头行：会话内写串行化
  next = SELECT COALESCE(MAX(seq), -1) + 1 FROM platform_session_events
         WHERE session_id = :sid                    -- 注意：聚合查询不允许带 FOR UPDATE
  INSERT (session_id, next, type, now(), data, ignorable, turn)
COMMIT
```

- **批量写窗口**：SSE chunk 类事件进内存队列，200ms 或满 64 条 flush 一次（单事务批插，
  dsh-02 B5）；flush 与会话结束时强制清空。
- **配对前置约束**：`assistant/message.source_event_seqs` 引用 chunk 的 seq，因此写
  `assistant/message` 前必须先强制 flush 该 step 的 chunk 队列、拿到已分配 seq；
  `tool/result` 引用 `tool/call` 同理（call 为即时写，天然满足）。
- **崩溃恢复**：启动扫描 `turn IS NOT NULL AND 无对应 turn/end` 的会话（实现注记：限定
  最近 7 天窗口，或对 `(session_id, turn)` 建部分索引，避免全表反连接扫描拖慢启动）→
  补合成 `turn/end {reason:'crashed'}` 与未闭合工具的 `tool/result {outcome:'unknown'}`
  （dsh-02 B4 的 TOOL_OUTCOME_UNKNOWN 语义）。
- 派生消息历史 `derive_messages(session_id)`：按 seq 折叠，规则见 §3.4。

### 2.3 `platform_compensations`（双写补偿，PLAN 8.3）

```sql
CREATE TABLE platform_compensations (
    id           BIGSERIAL PRIMARY KEY,
    session_id   UUID NOT NULL,
    event_seq    BIGINT NOT NULL,          -- 对应已落库的 submit 事件
    plugin_name  VARCHAR(64) NOT NULL,
    action       VARCHAR(128) NOT NULL,    -- 插件声明的补偿动作名
    payload      JSONB NOT NULL,
    status       VARCHAR(16) NOT NULL DEFAULT 'pending',  -- pending/done/failed
    retry_count  INTEGER NOT NULL DEFAULT 0,
    created_at   TIMESTAMPTZ NOT NULL DEFAULT now()
);
```

顺序铁律：**先写事件日志，后执行业务落库**；业务失败 → 写一条补偿记录，后台 worker
按事件重放补偿（详见 07 文档 §3）。

### 2.5 业务表三条红线（强制，CI 卡点）

适用于所有 `plugins/*/backend/models.py` 定义的业务表。平台表同样不执行 DELETE（会话仅
归档，`ON DELETE CASCADE` 仅供运维级硬清理）。

**红线 1：逻辑删除**
- 所有业务表必须有 `is_delete BOOLEAN NOT NULL DEFAULT FALSE`；
- **全代码库禁止 DELETE 语句**（含 ORM `query.delete()`）——删除 = `is_delete=true` 的
  UPDATE；CI lint 扫描 SQL 文本与 ORM 调用，违例即失败；
- 查询默认过滤 `is_delete=false`：由 db session 工厂全局注入（SQLAlchemy
  `do_orm_execute` 事件），插件无需手写。

**红线 2：审计字段**
- 所有业务表必须有：
  `created_by VARCHAR(64) NOT NULL`、`created_at TIMESTAMPTZ NOT NULL DEFAULT now()`、
  `updated_by VARCHAR(64) NOT NULL`、`updated_at TIMESTAMPTZ NOT NULL DEFAULT now()`；
- `created_at/updated_at` 默认取**数据库时间**；`updated_at` 由数据库触发器自动维护
  （Alembic 提供 `attach_updated_at_trigger(table)` 辅助函数，迁移必须调用）；
- `created_by/updated_by` 由 session 工厂从当前上下文用户自动填充，插件不传。

**红线 3：系统级操作日志**
- 业务表的所有 `select / insert / update` 必须落系统级日志（表见 §2.6），支撑后续
  "使用记录追溯"功能；
- 记录五要素：**什么时间**（occurred_at）、**什么地点/入口**（client_ip + entry_point）、
  **什么人**（user_id）、**做了什么**（operation + entity + record_key + detail）、
  **执行手段**（channel：page / agent / model / skill / mcp / tool / api / system，
  actor 记具体执行者如模型名/工具名）；
- 实现位置：insert/update 由 ORM flush 事件自动记录；select 由 session 工厂的查询包装
  记录（entity + 条件摘要 + 命中行数，**不记全量结果集**）；
- channel 由入口自动确定：REST 路由（页面操作）→ `page`；工具调用 → `tool`（actor =
  模型名+工具名）；后台 worker → `system`。插件业务路由复用同一 session 工厂即自动获得。

**模型基类**：`app/persistence/base.py` 提供 `BusinessBase`（含红线 1/2 全部字段）；
CI 检查：扫描 `plugins/*/backend/models.py` 与 Alembic 迁移，业务表未继承基类/缺字段/
缺触发器 = 失败。

### 2.6 `platform_operation_logs`（系统级操作日志）

```sql
CREATE TABLE platform_operation_logs (
    id           BIGSERIAL PRIMARY KEY,
    occurred_at  TIMESTAMPTZ NOT NULL DEFAULT now(),  -- 什么时间
    user_id      VARCHAR(64)  NOT NULL,               -- 什么人
    session_id   UUID,                                -- 所属会话（页面直连可为空）
    channel      VARCHAR(16)  NOT NULL,               -- page/agent/model/skill/mcp/tool/api/system
    actor        VARCHAR(128) NOT NULL DEFAULT '',    -- 具体执行者：模型名/工具名/技能名/路由
    plugin_name  VARCHAR(64),
    entity       VARCHAR(128) NOT NULL,               -- 业务表/对象
    operation    VARCHAR(8)   NOT NULL,               -- select/insert/update（无 delete）
    record_key   VARCHAR(128),                        -- 主键或业务键
    detail       JSONB        NOT NULL DEFAULT '{}',  -- insert:新值摘要; update:字段级old/new; select:条件摘要+行数
    client_ip    VARCHAR(45),                         -- 什么地点（来源 IP）
    entry_point  VARCHAR(128),                        -- 入口：API 路由 / 工具名 / job 名
    request_id   VARCHAR(64)
);
CREATE INDEX idx_oplogs_entity ON platform_operation_logs(entity, occurred_at DESC);
CREATE INDEX idx_oplogs_user   ON platform_operation_logs(user_id, occurred_at DESC);
CREATE INDEX idx_oplogs_sess   ON platform_operation_logs(session_id, occurred_at DESC);
```

- `detail` 落库前过脱敏瀑布（与 telemetry 同一脱敏管线，01 §2）；secret 字段值拒绝写入
  （与 07 §8 凭证规则共用同一校验器）。
- 本表自身 append-only：无 update、无 delete，仅按保留策略归档（M4 定）。

## 3. 事件词表 v1（pydantic 判别联合）

### 3.1 信封

```python
class SessionEvent(BaseModel):
    type: str
    seq: int
    time: datetime
    data: dict          # 由注册的 payload 模型校验
    ignorable: bool = False
```

surface 事件（`user/message`、`assistant/message`、`tool/result`、`component/submit`）
额外携带：`source_event_seqs: list[int]`（引用构建它的更早事件）与 `surface_op:
Literal['append','replace']`（compaction 替换用）——字段语义照抄 dsh-02 B1。

### 3.2 核心词表（框架拥有）

| type | data 要点 | surface |
|---|---|---|
| `turn/start` | `{turn}` | 否 |
| `turn/end` | `{turn, reason: completed\|blocked\|aborted\|error\|max_tokens\|crashed}` | 否 |
| `step/start` | `{turn, step}` | 否 |
| `step/end` | `{turn, step}` | 否 |
| `user/message` | `{content: str, source: 'human'\|'inject', origin?: {kind:'plugin',name}}` | 是 |
| `assistant/chunk` | `{turn, step, delta: str}` | 否（批量合并落库） |
| `assistant/message` | `{turn, step, content, usage?{prompt,completion}}` + source_event_seqs→chunks | 是 |
| `tool/call` | `{call_id, name, arguments}` | 否 |
| `tool/result` | `{call_id, name, content, is_error, outcome?: 'unknown'}` + source→call | 是 |
| `compaction/summary` | `{summary, replaced_seqs, est_tokens}` | 是(replace) |
| `component/request` | `{component_id, kind, version, props, interrupt_id}`（interrupt 桥，07 §2） | 是 |
| `component/submit` | `{component_id, action: 'submit'\|'cancelled', values?, summary}` + source→request | 是 |
| `feedback/record` | `{text}` 原文不解析（dsh-12 G） | 否 |

注：`component/submit-ack {component_id, event_seq}` 是 SSE 下行确认帧（03 §2），**不落日志**，故不入词表。

### 3.3 业务组件事件族（插件声明，框架校验）

命名规则：`<namespace>/<entity>-<verb>`（namespace 默认取插件 domain，可用 plugin.json 的
`event_namespace` 覆盖，全局唯一，05 §2）。每个事件族 = 一个 start + N 个 update + 终态。

**示例：财务填报（financial-report 插件）**

| type | data（payload 模型由插件 contract 提供） |
|---|---|
| `financial/form-start` | `{form_id, version:1, turn, company_ids:[], period, indicators:[{id,name,unit}], draft:{}}` —— **whole-value 快照**（dsh-01 A4：checkpoint 优先） |
| `financial/form-field-update` | `{form_id, version:1, draft: <完整草稿快照>}` —— 携带全量而非增量 |
| `financial/form-submit` | `{form_id, version:1, values:{...}, summary: "3 家公司 12 项指标"}` —— summary 是给模型的摘要（PLAN 8.5） |
| `financial/task-dispatched` | `{task_id, form_id, assignee, due}` |

规则（写进插件加载校验）：
- 每条事件必须携带稳定业务 id（`form_id`）——禁止"猜最近未完成的 Context"
  （dsh-01 附·acceptMatch 不变量）；
- update 按 seq 升序回放必须**确定性**产出同一状态；
- payload 模型必须 `model_config = ConfigDict(extra='forbid')`。

### 3.4 derive_messages 投影规则

模型上下文 = 按 seq 折叠：取 surface 事件 → `replace`（compaction）删除被引用 seq 的
节点 → `user/message(source='inject')` 折叠为一条摘要注入 → `component/submit` 投影为
`user: {summary}`（**只投影 summary 字段，明细留在日志**，PLAN 8.5）。
实现为带缓存的增量折叠（游标记到 seq，O(新事件)，dsh-02 附）；**`replace` 到达即缓存
整体失效重建**（replace 修改的是游标之前的历史；缓存 key 含最近一条 replace 的 seq）。

**上下文双轨边界（定死）**：运行中 Agent 的模型上下文由 **LangGraph 图内 state** 供给
（checkpointer 负责 resume）；`derive_messages` 服务于审计、UI 回放、compaction 输入与
对账。两侧必须满足"模型可见即已记录"：对账测试断言同一 turn 内图 state 消息与
derive_messages 投影一致。compaction 的实现位置见 07 §5（图内摘要节点 + 事件同步）。

## 4. 服务端投影（只读派生表）

`platform_projections(session_id, key, state_version, seq, value JSONB, PRIMARY KEY(session_id,key))`
——`stats`（turn/step/token/耗时）、`form_progress`（填报进度）等；
单元契约：`init/apply/view` 三纯函数 + `state_version`（bump 使旧行丢弃，dsh-12 D1）。

## 5. 事件版本化规则（PLAN 8.1 落地）

1. payload 必带 `version: int`（v1 起）；
2. 前端 renderer 按 `(type, version)` 分发；旧版本 renderer 永不删除；
3. 新需求 = 加新字段（可选）或发新事件 type（如 `financial/form-start-v2`），**永不改老
   字段语义**；
4. 契约测试断言：同 type 老版本的回放结果在新代码下不变。
